1.2 Background, as ISRO wrote it

“Accurate Digital Elevation Models (DEMs) and Digital Surface Models (DSMs) are fundamental to urban planning, disaster management, and military reconnaissance. Traditionally, elevation data is acquired through stereo-imaging pairs, LiDAR, or Interferometric Synthetic Aperture Radar (InSAR). These approaches can be cost-prohibitive, dependent on specific sensor availability, and computationally intensive. Single-view height estimation offers an agile alternative, but foundational monocular depth models are trained largely on natural egocentric imagery and predict relative depth. When applied to remote sensing, they face domain gaps, structural variations, and a lack of absolute-scale mapping. Converting relative depth into metric elevation remains a critical challenge, alongside the operational need to transform static elevation profiles into interactive 3D assets that can be navigated in real time.”

1.3 Description, as ISRO wrote it

“Develop an end-to-end software pipeline that transforms single-view optical RGB remote-sensing images into high-precision elevation maps. The framework must support both non-georeferenced and georeferenced imagery.”

  • Non-Georeferenced RGB Imagery (for example, PNG or JPG): produce a Relative Digital Surface Model (rDSM) for images without spatial metadata.
  • Georeferenced RGB Imagery (for example, GeoTIFF): produce an Absolute Digital Surface Model (DSM) with metric height values for images containing coordinate-system metadata.

“The solution should use a pre-trained monocular depth-estimation backbone to generate initial relative-depth maps. For georeferenced imagery, a lower-resolution DEM source such as SRTM or a limited set of Ground Control Points may be used to map scale-agnostic depth features to absolute metric elevations. For non-georeferenced imagery, relative height may be used directly in the visualization stage.”

“After computing the elevation map, the system should project the original optical image onto a generated 3D terrain mesh and integrate the result with a rendering engine such as Unity, Three.js, or Babylon.js. The interface should support seamless first-person navigation and analysis of structural heights and slopes from arbitrary aerial perspectives.”

1.4 The three key milestones

Elevation Extraction
Use a robust pre-trained monocular depth model to extract geometric and structural representations from single-view optical imagery.
Scale Calibration
Develop a module that converts relative depth to absolute height using scene-level statistics, low-resolution DEMs, semantic priors, or minimal Ground Control Points for georeferenced inputs.
Visualization Layer
Build an immersive, preferably interactive, rendering pipeline that converts the optical texture and derived depth map into a navigable 3D environment deployable as a standalone application.

Part 2

What the system does, end to end

One optical satellite image goes in. A navigable, measurable 3D surface comes out. This part traces every stage of that path and names the file that performs it.

2.1 The one-sentence description

The claim, stated precisely

DepthWizard takes a single optical satellite photograph and produces a per-pixel map of height above ground in metres, together with a per-pixel statement of how uncertain each of those metres is, then renders that map as a textured 3D surface a user can fly through and take measurements on in a web browser — with no graphics card anywhere in the chain.

2.2 Why one image is hard

Height from imagery is normally obtained one of three ways, and all three need something we are refusing to require:

Conventional methodWhat it needsWhy that is a problem
Stereo photogrammetryTwo photographs of the same ground from different anglesCannot be applied retrospectively. Decades of single-view archive imagery can never gain height.
Airborne LiDARA laser scanner flown over the areaExpensive, slow, requires a flight campaign per area.
InSARRadar satellite pairs with controlled baselinesSpecific sensor availability; computationally heavy.

Single-view height estimation is ill-posed: infinitely many three-dimensional scenes project to the same flat photograph. There is no unique correct answer. That is not a detail — it is the reason this project predicts a distribution per pixel rather than a number, which is covered in Part 5.

2.4 Stage by stage, with the responsible file

1. Ingest
tools/prepare_data.py unpacks the DFC2019 archives, measures what the documentation does not state (pixel size, void encoding, height range), and writes compressed shards. The probe step exists because the DFC2019 tiles were rewritten by tifffile at some point in their history and lost all georeferencing — nothing in the files says a pixel is 30 cm.
2. Split
Regions are assigned whole to train, validation or test with seed 1337. No tile from a training region can appear in validation. 76 / 16 / 16 regions.
3. Train
train.py fine-tunes Depth Anything V2 Small with a Gaussian negative-log-likelihood objective, two learning rates, and a software thermal governor for the GPU.
4. Score
tools/evaluate.py runs whole 1024×1024 tiles through a sliding window and reports RMSE, MAE, correlation, bias, per-semantic-class error, per-terrain error, per-building error, calibration error, and the σ-versus-error rank correlation.
5. Infer
infer.py runs a scene of any size: tiles it at 518×518 with 140 px overlap, blends with a cosine window, optionally applies 8-fold test-time augmentation, optionally fuses a second pass at 2× zoom, optionally matches the input resolution to the training resolution, optionally anchors to a coarse DEM or to ground control points. Writes GeoTIFFs.
6. Export
tools/export_terrain.py converts the rasters into a browser bundle: raw float32 binaries plus a JSON manifest carrying provenance, geometry, and every statistic the viewer's panels display.
7. Render
viewer/main.js builds a Three.js mesh from the float32 heights, drapes the original photograph over it, and provides four display modes, a drag-to-compare against LiDAR, an error map, a sun-direction control, a tour path, and a two-click measuring tool with calibrated error bars.
8. Serve
tools/serve_app.py exposes the whole thing publicly: the viewer, the baked scenes, and an upload endpoint that runs stages 5–6 on demand.
9. Package
tools/build_standalone.py inlines everything — Three.js, the application code, every scene binary, every texture — into a single 15.16 MB HTML file that runs offline from a double-click.

2.5 The two output products the problem statement asks for

PNG / JPG, no spatial metadatarDSM — relative surface modelThe model's height output is used directly. It is metric in the sense that the head was trained to regress metres, but with no location there is no datum to anchor it to, so it is reported as relative.

The distinction that most confuses readers

The model predicts AGL — above ground level, also called nDSM or normalised DSM. A 10 m building on a 100 m hill reads 10 m, not 110 m. That is deliberate: it is the quantity that transfers between places, because it does not depend on where sea level is. A DSM is elevation above a vertical datum, so producing one means adding the terrain back. Part 8.6 covers how.

2.6 What makes this more than a depth model with a camera flying through it

  1. Every pixel carries an error bar. The network predicts a Gaussian per pixel, trained with heteroscedastic negative log-likelihood. The claim is falsifiable and was tested: expected calibration error is 0.077 and the rank correlation between predicted uncertainty and actual error is +0.829.
  2. The viewer is a measuring instrument. Two clicks give ground distance, height difference and slope distance in metres, with the uncertainty on the height difference propagated — and calibrated, because the naive combination of two error bars is wrong by a factor of about 3.5 on a single rooftop.
  3. Heights survive the trip to the browser exactly. Terrain ships as raw float32, not as a 16-bit PNG. Browsers decode images through an 8-bit canvas and would silently quantise the metres.
  4. It runs with no GPU. ONNX export, int8 quantisation, CPU inference measured at 509 ms per 518×518 tile, and a live public deployment on a 2-vCPU virtual machine.

Part 4

The model

Depth Anything V2 Small, adapted to predict absolute height in metres with a per-pixel uncertainty. Every layer, every parameter count, and every initialisation decision.

4.1 What the base model is

Identifier
depth-anything/Depth-Anything-V2-Small-hf on Hugging Face
Licence
Apache-2.0. This is the only variant that can legally ship. Base, Large and Giant are CC-BY-NC-4.0.
Task it was trained for
Monocular relative depth estimation on natural, ground-level photographs.
Backbone
DINOv2 ViT-S — a vision transformer, patch size 14, embedding dimension 384.
Neck
DPT — Dense Prediction Transformer. Reassembles the coarse token grid back into a dense per-pixel feature map.
Constructed by
One call: AutoModelForDepthEstimation.from_pretrained(model_id). The backbone, neck and head are then taken apart and rewired.

What each of those words means

Vision transformer
A network that cuts an image into a grid of small squares (“patches”), turns each into a vector (“token”), and lets every token exchange information with every other token. Unlike a convolutional network it has a global view from the first layer.
Patch size 14
Each square is 14×14 pixels. This single number constrains everything downstream — see the input-size trap in 4.5.
Embedding dimension 384
Each 14×14 patch is represented by a vector of 384 numbers.
DINOv2
A backbone trained with self-supervision — no human labels at all. It learned general visual structure from a very large image collection, which is why it transfers to imagery it never saw, including satellite photographs.
DPT
The decoder design that takes transformer tokens at several depths and progressively fuses and upsamples them into a full-resolution prediction.

4.3 The four changes made to the stock model

Change 1 — two outputs instead of one

The stock head ends in a single 32→1 convolution. That convolution is kept and becomes the mean branch (conv_mu), because its weights are pretrained and worth keeping. A second 1×1 convolution is added as the log-variance branch (conv_log_var). Both share conv1 and conv2.

This is the standard Kendall & Gal arrangement for heteroscedastic uncertainty: one trunk, two thin heads, one predicting the value and one predicting how uncertain that value is. It costs almost nothing.

Change 2 — no final ReLU

The stock head clamps its output at zero, because relative depth cannot be negative. Height above ground is almost non-negative — but a hard ReLU has zero gradient everywhere it is active, so any pixel the model pushes below zero early in training is dead for the rest of the run. The ReLU is removed and the loss is left to handle plausibility.

Change 3 — output scaled to metres

The pretrained head emits values around 1. Height above ground runs to tens or hundreds of metres. Rather than force the head to learn a large gain through a 5×10-6 learning rate, the network predicts in normalised units and the result is multiplied by height_scale.

height_scale = 13.223477220535276

This is not a round number and not a guess. It is the 95th percentile of the above-ground height distribution measured across all 2,783 training tiles. The maximum would be wrong — that is a lone 204 m structure, and scaling by it would squash every ordinary building toward zero. The p95 puts the bulk of the distribution in a sensible numeric range.

The loss therefore sees metres directly, which means the RMSE printed during training is already the number ISRO scores, while the network's internal range stays around 1.

Variance is predicted in the same normalised units, so converting it to metres is a shift of 2·log(height_scale) in log space. Doing that inside the model rather than inside the loss keeps the loss unit-agnostic and the reported σ in metres.

Change 4 — a useful accident of polarity

Depth Anything V2 predicts inverse relative depth: nearer is a larger number. Viewed from orbit, nearer means taller. So the pretrained head's sign convention already matches height, and the fine-tune starts from a sensible initialisation rather than fighting one.

4.4 Initialisation, and why each choice is deliberate

conv_log_var weights
Initialised to zero, bias to 2·log(init_sigma / height_scale) with init_sigma = 5.0 m. So σ starts uniform at 5 m everywhere and only becomes spatially varying once the data gives it a reason to. Random initialisation here lets the variance term shove the mean head around before the mean head knows anything.
conv_mu, default
init_mu="pretrained" — keeps the pretrained readout. This is what runs 01–04 used, and keeping it as the default means those runs stay bit-comparable.
conv_mu, alternative
init_mu="constant" — zero the weights and set the bias to a chosen constant height. Added after run05 died. See below.
The initialisation bug that cost nine GPU-hours

The pretrained readout emits disparity, and its output scale is a property of the checkpoint's feature magnitudes, not of the task. Measured on real crops with tools/preflight.py: the median absolute residual at initialisation is 16.5 m for DA-V2-Small but 666 m for DA-V1-Large. The two model families' necks do not emit features of the same magnitude, even though their conv3 weights are comparable in size (mean |w| 0.088 against 0.100).

A 666 m residual drives log_var into its clamp on the very first NLL step. The clamp then zeroes the variance head's gradient and suppresses the mean head's by roughly 1,100× (measured by tools/nll_deadlock_probe.py). That is what killed run05: it diverged to NaN at epoch 6 and produced no information at all. The fix is init_mu="constant", which discards a 32→1 linear readout of disparity that would have to be relearned as height anyway, while keeping the backbone, the neck and conv1/conv2.

4.5 The input-size constraint — a trap that fails silently

Patch size 14 governs every image dimension in this project

The head computes patch_h = H // 14 and then interpolates its output to patch_h × 14. Feed it a 256×256 crop — the size the Depth Any Canopy recipe uses — and you get 252×252 back, with no warning and no error.

Crops are therefore 518, which is 14 × 37 and is also DA-V2's native training resolution. A stride of 506 tiles a 1024×1024 image exactly 2×2. model.check_input_size() raises a ValueError naming the nearest valid sizes rather than letting a mismatch reach the loss, where it would surface as a confusing broadcast error or, worse, silently work after an accidental resize.

4.6 The forward pass, in order

1.  check_input_size(H, W, 14)                     raise if not a multiple of 14
2.  ph, pw = H // 14, W // 14                       token grid dimensions
3.  out = backbone.forward_with_filtered_kwargs(x)  DINOv2 ViT-S -> feature maps
4.  hidden = neck(out.feature_maps, ph, pw)         DPT reassemble + fuse
5.  feat = hidden[head_in_index]                    head_in_index = -1, the last stage
6.  x = conv1(feat)                                 64 -> 32 channels
7.  x = interpolate(x, (ph*14, pw*14), bilinear)    upsample, exactly as in the DPT paper
8.  x = activation1(conv2(x))                       32 -> 32, ReLU
9a. mu      = conv_mu(x) * height_scale             metres
9b. log_var = conv_log_var(x) + 2*log(height_scale) log-variance in metres-squared
10. return mu, log_var

model.predict() wraps this, converts log-variance to sigma = exp(0.5 · log_var), and returns (height_m, sigma_m) as two (B, 1, H, W) tensors.

4.7 The optional binned head (built, measured, not shipped)

A second head design exists behind --bins N, defaulting to 0 (off). It implements the architecture from HTC-DC Net, IEEE TGRS 2023:

Adaptive bins
A small MLP over the pooled feature map predicts N bin widths per image via softmax, so widths are strictly positive and always sum to the full height range. Edges are the cumulative sum from bin_min.
Soft-argmax
The output is the expectation H = Σ Pᵢcᵢ over bin centres — a continuous value from a classification head, with no discretisation artefacts.
Head-tail cut
Foreground is defined as height > 1 m. Foreground and background get their own distribution over bins, selected per pixel by a binary classifier. Measured on our shards, 35.6% of valid pixels sit above 1 m, so the binary problem is close to balanced.
Warmup routing
During the first 500 steps the ground truth does the routing, not the gate. Measured at initialisation, a randomly initialised gate fired on either 0.0% or 99.4% of pixels depending on the random projection — whichever branch loses gets no gradient at all. Truth-routing removes that lottery.
Configuration
N = 128 bins over a measured range of [−3, 120] m. 128 rather than the conventional 256 because ablations show gains saturate early and 128 is what fits in 12 GB at 518×518.

It lost. run03 scored 6.950 m whole-tile against run02's 6.454 m — 7.7% worse overall and 8.8% worse on buildings, which is the thing it was built to fix. The full result is in Part 13. The code is kept because it exports to ONNX cleanly and is the right starting point if the approach is revisited.

Part 5

The loss functions

Why the model predicts a distribution rather than a number, what each loss term buys, and the tests that prove the uncertainty head recovers a known answer.

5.1 The core objective — heteroscedastic Gaussian negative log-likelihood

L = 0.5 * ( log_var + (y - mu)^2 / exp(log_var) )

Read the two terms as a trade. The model can lower the residual term by admitting uncertainty — but it pays log_var for doing so. It cannot buy a free pass by predicting huge variance everywhere, because the first term grows.

Heteroscedastic means the uncertainty is predicted per pixel rather than being one number for the whole image. That is the useful version: a flat car park and a cluttered rooftop edge genuinely do not deserve the same error bar.

Predicting log-variance rather than variance keeps it positive without a clamp and keeps gradients well-scaled.

log_var range
Clamped to [−7, +7] (--log-var-max 7.0). Guards against exp() overflow and against the model escaping into “infinitely uncertain everywhere.”
Validity mask
Every loss takes a mask. LiDAR void pixels and no-data regions contribute nothing.
Gradient clipping
Norm clipped at 1.0 (--clip).
Rail tripwire
If log_var sits at its clamp for --rail-patience 50 consecutive steps, the run aborts. This is the guard that run05 did not have.
Sanity gates
A run is killed if RMSE exceeds --gate-rmse 25.0 or correlation falls below --gate-corr 0.20. tools/tripwire_selftest.py proves both that the tripwires fire on a broken run and that they do not fire on a healthy one.

5.4 The test that proves the uncertainty head works

Recovery of a known heteroscedastic sigma

A synthetic dataset is built with two regions of deliberately different noise: true σ = 0.50 in one and 3.00 in the other. The head is trained on it and asked what σ it thinks each region has. It recovers 0.497 and 2.99, and separates the two regimes with a ratio of 6.02 against a true ratio of 6.0.

This matters because “the model reports uncertainty” is a claim that is easy to make and hard to check on real data, where the true uncertainty is unknown. On synthetic data the true answer is known, and the head returns it.

Test suite status, run on 6 September 2026: tests/test_losses.py reports 19 passed, 0 failed. tests/test_gcp_affine.py reports all 9 tests passed, including exact recovery of a known ratio error — a fitted exponent of 1.3889 against a true 1.3889, with a residual root-mean-square of 7.74×10-7 m.

Both files must be run with PYTHONPATH set to the repository root; there is no pytest in the virtual environment, and each file carries its own __main__ runner.

5.5 Why uncertainty is a differentiator and not decoration

Single-view height is ill-posed. A model that outputs one confident number per pixel is hiding that fact. Three consequences make the uncertainty head worth its 33 parameters:

  • It scores in both halves of the marking scheme. It is an accuracy claim (“calibrated confidence”) and a visualisation feature (a display mode in the viewer).
  • It is operationally usable. The rank correlation between predicted σ and actual error is +0.829. Where the model says it is unsure, it is wrong, monotonically. That makes the uncertainty layer usable for triage — deciding which parts of an output need a human to look at them.
  • It feeds the measurement tool. A height difference between two clicked points carries an error bar derived from the two σ values, which is what turns a picture into an instrument.

7.7 The thermal problem, and how it was actually solved

Unregulated, the RTX 3060 reached 91 °C in under ten minutes and down-clocked itself from 1875 MHz to 1492 MHz. The “full speed” run was not faster, only hotter. nvidia-smi -pl is the clean fix but needs an administrator shell, so train.py carries a software ThermalGovernor: sample every N steps, pause proportional to overshoot, hard-stop above a ceiling until it cools.

The software governor was a workaround for a settings bug

MSI Afterburner has a Prioritize switch between power and temperature, and it defaults to power — which makes the temperature limit advisory. The card draws to its power limit and lets temperature land wherever it lands. That is why a limit of 77 °C still produced 91 °C readings, and why raising the fan from 62% to 85% bought only about 3 °C.

Never change GPU settings while a CUDA job is running

Applying Afterburner settings resets the display driver and invalidates live CUDA contexts. Doing it mid-run killed a training process with torch.AcceleratorError: CUDA error: unknown error and silently reverted the power limit to 170 W.

7.8 Built for interruption

Kaggle sessions are capped at 12 hours and can be reclaimed sooner, so everything assumes the process may die at any moment:

  • State is checkpointed every epoch and on a wall-clock budget (--max-hours).
  • --resume auto restores model, optimiser, scheduler and RNG state.
  • The metrics log is append-only JSONL, so a partial run still plots.
  • Preprocessing is done locally — it is CPU and disk bound and burns zero GPU quota — then shards are uploaded once as a Kaggle Dataset and every session mounts them instantly.
  • Code lives in git and is cloned into notebooks. Code is never written inside a notebook.

7.9 Preflight — refusing to start a broken run

tools/preflight.py exists because run05 burned nine GPU-hours producing nothing. It measures the initial residual before a run begins, and it is the tool that revealed the 16.5 m against 666 m difference between DA-V2-Small and DA-V1-Large. A long run that is already broken at step zero is now refused rather than discovered six epochs later.

8.3 Resolution fusion

--fuse-zoom 2 --fuse-sigma 8 runs a second pass at 2× magnification and fuses it with the first using a Laplacian split: the low-frequency component (smoothed with a Gaussian of σ = 8) comes from the native-resolution pass, and the high-frequency detail comes from the zoomed pass.

A deliberate trade, made because half the marks are visualisation

Fusion costs +0.051 m of per-building RMSE — 1.4% against TTA alone, and buys +28% edge definition: buildings read as flat-topped blocks rather than rounded mounds. It also improves bias and calibration slightly.

The fused numbers are the ones reported, because whatever is shipped must be what is scored. Reporting the better 3.616 m while shipping the 3.667 m configuration would be dishonest by a margin larger than the difference.

8.5 Auto-zoom — surviving a different evaluation resolution

We train at 0.3 m. ISRO will evaluate on their own imagery, likely nearer 0.6–1.0 m. Untreated, that costs a great deal: a backbone token then covers twice the ground, and buildings get averaged with their surroundings.

One token is 14 pixels. At 0.3 m per pixel that is 4.2 m of ground per token. At 0.6 m it becomes 8.4 m — wide enough to swallow a small house whole.

8.6 DEM anchoring — producing an absolute DSM

--dem auto turns above-ground heights into absolute elevation:

DSM = terrain elevation (Copernicus GLO-30) + our above-ground height
Tile discovery
dem.tiles_for_bounds() returns every 1°×1° GLO-30 tile touching the scene's bounding box. A scene straddling a tile edge is normal, not exotic — assuming one tile is how a coastal or border scene ends up with half its elevation missing and no error raised.
Tile naming
Copernicus_DSM_COG_10_N27_00_E088_00_DEM — constructed from the floor of the latitude and longitude.
Access
Read over HTTPS through GDAL's /vsicurl/, windowed, so only the needed bytes are fetched.
Resampling
Cubic, onto the scene's own pixel grid.
Datum handling
Terrain is stored relative to a datum (terrain_datum_m in the manifest), or the mesh sits 1.3 km from the origin and every camera default aims at empty sky.
Bare-earth option

Default state
Off in the public deployment. --dem auto reaches Copernicus during a request that already takes a minute, so it is opt-in per deployment rather than a surprise timeout.

8.7 Ground control point calibration

The problem statement names “a limited set of Ground Control Points” as an acceptable route to absolute scale. This is implemented and, importantly, measured.

Affine is the wrong functional form

The model's error is a height-dependent ratio — 1.20× at 0–3 m, falling to 0.52× above 40 m. No straight line can be above 1 at one end and below it at the other. Measured head to head on held-out buildings, per tile, over the 10 validation tiles containing a building above 20 m:

FormControl points (k)RMSEvs uncalibratedMAETiles made worse
uncalibrated—7.248 m—4.013 m—
affine86.154 m−15.1%4.477 m8 of 10
power55.730 m−20.9%4.202 m4 of 10
power85.442 m−24.9%4.038 m5 of 10

Affine buys RMSE by spending MAE (+11.6%); the power law takes more RMSE and leaves MAE where it found it (+0.6%). Over all 57 usable tiles the power law is the only form that beats doing nothing at all (−4.4% against affine's +0.1%).

Guards, calibrated against the measurement rather than chosen

  • At least 2 control points must lie in the upper 60% of their height span. Requiring the upper half would refuse 24.6% of the draws that produced the gain; the upper 60% refuses 6.3%.
  • The fitted exponent must be ≥ 0.95, which is what catches “this fit would compress the heights further.”
  • Control values are read as a structure median — region-grown from the clicked point — not a fixed patch. On one Omaha tile a point sample returned 0.59 m where the truth was 5.6 m.
Honest end-to-end status

On the real tiles tested, the guards decline and the system falls back to offset-only. On OMA_288_012 the fitted exponent is 0.40–0.57 because that tile under-predicts everything; on JAX_165_018 it is 0.505 because the model is already good there. Both refusals are correct. It never degrades a result — it helps only when control points carry building-level heights and the scene genuinely spans a height range.

A selection trap worth remembering

The first probe required 25 buildings per tile and looked clean. It was worthless: those 36 tiles contain zero buildings above 20 m (RMSE 1.381 m), while all 60 tall buildings sit in tiles with fewer (RMSE 8.487 m). Dense suburbs have many small buildings and downtowns have few large ones, so a threshold chosen for sample size excluded 100% of the problem.

AGL is terrain-removed by definition, so a correct model reads the same on a rooftop at 1,200 m as on one at 400 m. Flat Jacksonville and Omaha can never test that. Copernicus GLO-30 over this crop gives 947 m of relief at a median slope of 31.4°.

Three method choices that change the answer

  • Per building, not per pixel, because their footprint edges are Sentinel-2 blurry and a pixel score would mostly measure their blur.

  • A global shift is recovered by FFT phase correlation first, because at 26° off-nadir a roof sits about 5 m from its own footprint while theirs come from near-nadir Sentinel-2. Erosion was a hypothesis, and it was wrong

Shrinking their footprint was expected to strip a blur halo and move the bias toward zero. Measured: −1.92 m at 0 m erosion, −2.72 at 2 m, −3.14 at 3 m — the wrong direction, because erosion drops small components first and so selects for the taller buildings we under-call most. The 3D viewer

Half the marks. The design rules it is built to, every feature, every label, and how it becomes a single double-clickable file.

10.1 What is being scored

ISRO's wording: “projection accuracy, visual fidelity, navigability of the flythrough, interface intuitiveness, stability, and successful standalone deployment.” That is 50% of the total marks.

10.2 The three rules that outrank every feature

1. Usable without explanation
A juror should understand what they are looking at in five seconds, with no caption, no legend to study, and no term they have to already know. If a control needs explaining, the label is wrong. This does not mean hiding the rigour: the plain word goes on the button and the precise number goes in the readout. “How sure we are, ±2.1 m” beats “sigma (m)” and carries strictly more information.
2. No decoration that carries no information
No purple gradients, no glassmorphism, no emoji headings, no hero section, no controls that exist to look busy. The jury are Space Applications Centre image-processing specialists who have used QGIS for twenty years. The data is the only saturated thing on screen; the interface stays near-neutral. Never a rainbow or jet colormap — it is the classic amateur signal in remote sensing.
3. Light theme
It survives a projector in a demo hall, screenshots drop into a submission PDF without inverting, and it puts the viewer in the same visual register as QGIS and ArcGIS Pro rather than a game engine.

Two things a light background forces, both done: the canvas is #eef1f4 and never pure white, or the surface silhouette disappears and every edge glares; and the ramps run light→dark rather than dark→bright, or the low end dissolves into the page. All three ramps are monotonic in lightness, so they survive greyscale printing. Ambient light is set much stronger than a dark scene needs (hemisphere 1.15) or the terrain reads as a dark blob cut out of the page.

Why height boost exists, and why it is not cheating

Why raw float32 and not a PNG

Browsers decode images through an 8-bit canvas. A 16-bit PNG of heights would be silently quantised on the way in, and the metres would stop being metres. Raw Float32Array over fetch is the only transport that preserves them exactly.

What the manifest carries

Provenance and geometry: the model that produced it ("run02 + TTA"), the CRS and affine transform, the bounds, pixel size and its units, the ground sample distance and where that GSD came from ("gsd_source": "--gsd flag"), the extent in metres, the vertical exaggeration baked in, and how many void pixels were filled.

Statistics the panels display: height minimum and maximum, sigma minimum, maximum and mean, truth minimum and maximum, per-pixel RMSE / MAE / bias / 95th-percentile absolute error, building and ground per-pixel RMSE, the building pixel count, and a full building_wise block with the number of buildings, RMSE, MAE, bias, median absolute error, correlation, and the truth median and 90th-percentile heights.

Each numeric block carries a note explaining what it is comparable to. For example the per-pixel error note reads: “per-pixel, whole tile. Roof edges dominate; per-building error is the comparable figure.”

11.4 Staging — what gets deployed

python deploy/stage.py assembles the deployable tree. Total context: 336.3 MB. Three things dominate the size and each is handled:

Checkpoint stripped
297.1 MB → 99.2 MB. best.pt carries optimiser state, scheduler state, RNG state and the training arguments — everything needed to resume a run and nothing needed to serve one. Kept: model, model_id, height_scale, model_config, epoch, val. Epoch and val are kept because infer.py prints them, and a served result that cannot name its checkpoint is not evidence.
HF cache baked in
model.py builds the backbone with from_pretrained(), which reaches Hugging Face on a cache miss. blobs/ is dropped because an HF cache stores every file twice — once under its SHA, once as a snapshot link — and only the snapshot is resolved at load time. HF_HUB_OFFLINE=1 turns any surviving download into a loud failure instead of a slow first request.
Uploaded scenes excluded
upload_* scenes are produced at runtime and sit in the same directory as the baked ones. Without the filter the deployment would ship whatever happened to be on the development machine. index.json is pruned to match, since an entry with no directory makes the viewer fetch a missing manifest and presents as the whole picker being broken.

stage.py refuses to build a context with zero baked scenes rather than deploying an empty picker. The zip is built at compression level 1 on purpose: the bulk is .pt, .safetensors, .bin and .jpg, none of which compress, so level 9 buys a percent or two for several minutes.

11.7 Limits the server enforces

Not decoration: one request costs CPU-minutes, so an unbounded queue is a way to take the site down by being mildly popular.

Why an area cap when there is already a byte cap

Because the two are barely related for satellite imagery, and only one of them predicts cost. A Maxar visual strip is 17408×17408 — 303 megapixels — in 12 MB, sparse and JPEG-compressed inside the TIFF. It passes a 50 MB byte cap comfortably and then needs about 2.8 hours, so the job used to sit there and time out at 600 s having told the user nothing in the meantime.

The cap is derived, not a magic number:

FIXED_S + megapixels * SEC_PER_MPX  <=  BUDGET_FRAC * DW_TIMEOUT

FIXED_S      = 25 s     checkpoint load, export, four array writes
SEC_PER_MPX  = 33 s     from the 1024x1024 upload that takes 60 s on this plan
BUDGET_FRAC  = 0.8
TTA_FACTOR   = 11.4     57.2 s / 5.02 s -- drops the ceiling to ~1.2 Mpx in accurate mode

So the limit moves correctly if the timeout or the plan changes. The refusal is immediate and specific: it names the dimensions, the projected time, and the size to crop to. Reading the header also catches a truncated or still-downloading GeoTIFF in the same millisecond, instead of forty seconds into inference with a TIFFReadEncodedTile traceback.

A refusal does not consume the caller's turn

Only an accepted job counts against per-IP spacing. Rejecting someone and then making them wait twenty seconds to try a smaller crop would be a worse experience than not having the guard at all.

Baked scenes are never reaped. Per-IP spacing reads X-Forwarded-For, which is client-supplied and therefore spoofable — that is fine, because it only paces polite users apart, and the queue cap is what actually bounds the work.

11.9 Persistence behaviour, measured twice

Uploaded scenes survive az webapp restart

Measured twice on 6 September 2026, contrary to the assumption written down first. A restart reuses the extracted tree under /tmp/<hash>/, so runtime scenes persist.

What does clear them is anything that recreates the container — an SSL bind or a redeploy — because the platform extracts a fresh tree and stage.py excludes upload_*.

So DW_SCENE_BUDGET is the only routine bound on disk growth, and a visitor's upload stays publicly listed until twelve more push it out. There is no delete endpoint; if a specific scene must go before then, redeploy.

11.10 Known gaps in the deployment

  • The model reloads on every request, costing about 8 s of every upload, because run_job shells out to infer.py exactly as the local tool does. Holding it resident means reimplementing the auto-zoom, fusion and DEM logic inside infer.py's main(), and duplicating the inference path is how a served result quietly stops matching the measured one. It stays until infer.py exposes a reusable entry point.
  • DEM anchoring is off by default (DW_DEM=1 to enable), because --dem auto reaches Copernicus during a request that is already slow.
  • The viewer does not yet warn about oversized images before upload, even though /api/capabilities publishes max_megapixels. The server refuses correctly; the client could refuse sooner.

A nadir view of a rooftop does not contain that information. That is the finding, and it is a stronger claim than “we ran out of time.”

13.3 Shadow — the new cue, taken to its ceiling

The obvious escape is a physical cue, and the metadata for one exists: 67 WorldView-3 .IMD files carry solar geometry, sun elevation spanning 23.4°–74.5°. height = shadow_length × tan(sun_elevation) is how photointerpreters measured buildings before computers, and its error profile is the inverse of ours — shadow is most precise on exactly the tall buildings where the network fails.

The cue is really there. Marching away from the sun on the tallest building in OMA_288_012 gives luminance 166 on the roof, 93–113 held for about 120 px, then 254 on lit ground. Marching toward the sun leaves the tile immediately.

QuestionMeasurement
Would perfect shadow segmentation be enough?No. Oracle shadows ray-cast from the truth DSM give r 0.503, slope 0.583, RMSE 2.61 m over 675 buildings. Our network already achieves r 0.787 per building.
How close is real detection to that oracle?Not close. Luminance + Otsu thresholding scores IoU 0.187 (precision 0.204, recall 0.689).
Is occlusion the limiter on tall buildings?No. Across the ten tiles richest in tall stock, all 10 components above 20 m had unobstructed shadow paths.
Then what is?Population. Those ten tiles hold 10 buildings above 20 m out of 766; the whole validation set holds about 60.

So the ceiling on the cue sits below the model we already have, and the population available to validate any tall-building method is about sixty buildings. That is why the tail stays in Limitations rather than being quietly fixed.

13.5 What the literature changed

A targeted literature search on 27 August 2026 contradicted two decisions already taken:

  • Our failure mode is the known failure mode of this field. HTC-DC Net states it directly: “the distribution of height values is long-tailed… trained networks are usually biased and tend to underestimate building heights… predictions can include many fatal cases for higher objects with incredibly large errors.” That is our error profile verbatim.
  • The fix is not loss reweighting. Every paper that moves the needle reformulates the output space. Hours had gone into designing a β-NLL reweighting fix with a two-hour GPU run already committed to it. One search surfaced the paper that named the failure, showed reweighting is the wrong class of fix, gave the method that works, and revealed that published DFC19 numbers are not comparable to ours at all.
  • Soft-argmax needs distribution supervision or it will not help. A roof edge is exactly a foreground/background bimodal pixel — the truth is either roof height or ground, never the average. Supervising only the mean lets the network put mass on both modes and bleed the edge.

This is why the repository carries a standing rule: search the literature before spending compute.

Part 14

Limitations and unfinished work

Stated plainly. Every one of these should be said out loud before a judge finds it.

14.1 Accuracy limitations

  1. Buildings above 20 m are under-called by about 17 m. Data scarcity, proven by probe 01. Training data tops out at 82.8 m while validation reaches 155.3 m. The direction is conservative — we are never too tall.
  2. Forested ground carries 2.5 m of error because a camera cannot see through canopy, while the LiDAR reference can. That is optics, not a model defect.
  3. Tile borders are worse — outer-pixel RMSE is roughly double the interior. A known property of patch-based vision-transformer inference.
  4. The absolute DSM anchor is itself a surface model. Copernicus GLO-30, like SRTM, includes buildings and canopy, so dense urban composites double-count part of the building height. --dem-bare approximates a correction and says that it is one.
  5. No Indian LiDAR. Everything over India is cross-checked against another model and is labelled as agreement, never as accuracy.
  6. The test split is unscored. By design, until the very end, once. It is also materially easier than validation.
  7. Urban RMSE is 13.9 m, four to seven times the other landscapes — and cities are where disasters concentrate. The honest framing: correlation stays at +0.808, so the shape is right and the scale of tall structures is not; and 94% of the building stock is under 10 m where the error is 1.4 m.

14.2 Coverage limitations

  • Two American cities. All LiDAR-verified accuracy comes from Jacksonville and Omaha. Both are flat.
  • No hilly LiDAR anywhere. The hilly case is Sikkim, which has no reference data, so it is a cross-check.
  • GAMUS is not trained on. The sponsor's recommended dataset is ingested to 200 tiles and blocked on disk. No model in this project has seen a GAMUS tile.
  • Cross-sensor generalisation is untested. Final evaluation uses ISRO imagery at an unknown resolution. --auto-zoom addresses the resolution part, measured on DFC2019 downsamples — not on real ISRO data, which we do not have.

Part 16

Glossary

Every term and abbreviation used anywhere in this document or in the project, in plain English.

Height and terrain
DSM
Digital Surface Model. A map of how high everything is, including buildings and trees. This is what ISRO asked for.
DEM
Digital Elevation Model. A general term for height data.
DTM
Digital Terrain Model. The bare ground, with buildings and trees removed.
rDSM
Relative DSM. The shape of the surface with no absolute datum. What we produce for a photo with no location data.
AGL / nDSM
Above Ground Level, also called a normalised DSM. How tall something is compared to the ground right underneath it. A 10 m building on a 100 m hill is 10 m AGL. This is what our model predicts.
Vertical datum
The zero surface elevations are measured from — roughly, sea level.
Vertical exaggeration
Stretching heights in the 3D view so the shape is visible. Ours starts at 1.5× and is removed before any measurement is reported.
Relief
The total height range across a scene. Sikkim's 2 km crop has 947 m of relief.
Imaging
GSD
Ground Sample Distance. How much ground one pixel covers. 0.3 m GSD means each pixel is 30 cm across. Smaller means sharper.
Nadir
Looking straight down. What satellites usually do, and why depth models struggle — there is no horizon or perspective to judge scale from.
Off-nadir
Looking at an angle. At 26° off-nadir a roof sits about 5 m from its own footprint.
Monocular
Using one image only.
Stereo
Using two photographs from different angles to work out height. The normal method, and the one being replaced.
LiDAR
A laser scanner, usually flown on an aircraft. Measures distance by timing a light pulse. Our source of correct answers.
InSAR
Interferometric Synthetic Aperture Radar. Radar-based elevation measurement, named in the problem statement.
Photogrammetry
Measuring real-world sizes and distances from photographs.
Orthoimage
An aerial image corrected so that every pixel is viewed as if from directly above.
Georeferenced
A photo that knows where on Earth it was taken.
GeoTIFF
An image file with location information built into it.
CRS
Coordinate Reference System. The definition of what the coordinates in a file mean.
COG
Cloud-Optimised GeoTIFF. Structured so a client can fetch just the part it needs over HTTP.
Megapixel
One million pixels. This determines processing time — not the file size.
Machine learning
Neural network
A program that learns patterns from examples instead of following written rules.
Backbone
The part of the model that understands the image. 89% of ours.
Neck
The part that turns the backbone's coarse output back into a dense per-pixel feature map. 10.9% of ours.
Head
The small final part that turns features into the answer. 0.1% of ours, and the part we modified.
Vision transformer (ViT)
A network that cuts an image into small squares and lets every square take account of every other square. Ours uses 14×14 pixel squares.
Token / patch
One of those squares, and the vector representing it.
DINOv2
The specific backbone inside Depth Anything. Learned from images with no human labelling, which is why it works on many kinds of picture.
DPT
Dense Prediction Transformer. Turns a coarse grid of tokens back into a full-detail answer for every pixel.
Fine-tuning
Taking a model someone else trained and continuing to train it on your own data. This is what makes our model output metres.
Zero-shot
Using a model with no extra training at all.
Checkpoint
A saved file containing a trained model.
Epoch
One full pass over the training data.
Step
One batch of examples, one weight update. run02 took 11,532 of them.
Learning rate
How large a change each step makes.
Weight decay
A pull toward smaller weights, which discourages memorisation.
AdamW
The optimisation algorithm used here.
Overfitting
Memorising the training examples instead of learning the general pattern.
Region-disjoint split
Splitting data by geographic area so no place appears in both training and testing.
Augmentation
Showing the model transformed copies of each example. D4 is the eight symmetries of a square.
TTA
Test-Time Augmentation. Running the same image through several times, flipped and rotated, then averaging. Slower but more accurate.
Sliding window
Processing a large photo as overlapping small squares, because the model only accepts a fixed size.
Ill-posed
A problem with more than one possible correct answer.
Heteroscedastic
Uncertainty that varies from place to place, rather than one number for the whole image.
NLL
Negative Log-Likelihood. The training objective: how surprised the model is by the true answer, given the distribution it predicted.
Soft-argmax
Turning a distribution over bins into a single continuous number by taking its expectation.
Ensemble
Averaging several models. Only helps when they make different mistakes; ours make the same ones (r = 0.925).
ONNX
A standard file format for neural networks. Lets our model run without installing PyTorch.
Quantisation
Storing the model's numbers with less precision to shrink the file. Ours saves 63% of the size and costs 0.161 m of accuracy.
bf16 / fp16 / fp32
Number formats of decreasing speed and increasing precision. bf16 needs Ampere or newer.
Metrics
RMSE
Root Mean Square Error. Square every mistake, average, take the square root. Because of the squaring, a few big mistakes push this up a lot.
MAE
Mean Absolute Error. The plain average mistake. Always smaller than RMSE. A big gap between the two means a few large mistakes dominate.
Bias
Whether you are consistently too high or too low. Ours is 17 m too low for buildings over 20 m.
Correlation (r)
How well predictions follow the real pattern, from −1 to +1. High correlation with bad RMSE means the shape is right but the scale is wrong.
Calibration
Whether the model's stated confidence matches how often it is actually right.
ECE
Expected Calibration Error. How far the stated confidence is from the observed frequency. Ours is 0.077.
Sigma (σ)
The model's own statement of how unsure it is about a pixel, in metres.
Rank correlation
Whether the ordering matches, ignoring exact values. Ours between σ and error is +0.829.
IoU
Intersection over Union. How well two shapes overlap. Shadow detection scores 0.187.
Oracle
A pretend perfect version of something, used to find the best a method could possibly do. An oracle result is never deployable.
Compression slope
How much the model squashes the height range. 1.0 would be perfect; ours is 0.471.
Project and infrastructure
GCP
Ground Control Point. A place where the true height is already known, used to correct a scene.
SRTM
A free worldwide elevation map from a Space Shuttle mission in 2000. Named in the problem statement.
Copernicus GLO-30
The free European worldwide elevation map we use instead. Same 30 m detail as SRTM, no account needed, and it covers the far north where SRTM has gaps.
CartoDEM
ISRO's Indian elevation map. Free only to Indian government bodies, so not available to us.
FABDEM
A true bare-earth product. Non-commercial licence, so not used.
DFC2019
Our training dataset. Aerial photos of Jacksonville and Omaha at 0.3 m per pixel, with laser-measured heights.
GAMUS
The dataset ISRO's own page recommends. Philadelphia, New York and Washington DC — all dense cities.
Mesh
The 3D surface built from the height numbers.
Texture drape
Painting the original photo onto that 3D surface so it looks real.
Hillshade
Artificial shading from a chosen sun direction, which makes relief legible.
Oryx
Azure's build system. Installs Python dependencies on the platform — and runs the app from /tmp, not wwwroot.
SNI
Server Name Indication. The TLS binding mode used for the custom domain.
ACR Tasks
Azure Container Registry's cloud image builder. Barred on Azure for Students.

AMD's hardware virtualisation switch in the BIOS. Off on this machine, which is why Docker cannot run.
RSS
Resident Set Size. How much RAM a process is actually using. Ours peaks at 2.21 GB.
