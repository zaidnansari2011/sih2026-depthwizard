1.2 Background, as ISRO wrote it

“Accurate Digital Elevation Models (DEMs) and Digital Surface Models (DSMs) are fundamental to urban planning, disaster management, and military reconnaissance. Traditionally, elevation data is acquired through stereo-imaging pairs, LiDAR, or Interferometric Synthetic Aperture Radar (InSAR). These approaches can be cost-prohibitive, dependent on specific sensor availability, and computationally intensive. Single-view height estimation offers an agile alternative, but foundational monocular depth models are trained largely on natural egocentric imagery and predict relative depth. When applied to remote sensing, they face domain gaps, structural variations, and a lack of absolute-scale mapping. Converting relative depth into metric elevation remains a critical challenge, alongside the operational need to transform static elevation profiles into interactive 3D assets that can be navigated in real time.”

1.3 Description, as ISRO wrote it

“Develop an end-to-end software pipeline that transforms single-view optical RGB remote-sensing images into high-precision elevation maps. The framework must support both non-georeferenced and georeferenced imagery.”

  • Non-Georeferenced RGB Imagery (for example, PNG or JPG): produce a Relative Digital Surface Model (rDSM) for images without spatial metadata.
  • Georeferenced RGB Imagery (for example, GeoTIFF): produce an Absolute Digital Surface Model (DSM) with metric height values for images containing coordinate-system metadata.

“The solution should use a pre-trained monocular depth-estimation backbone to generate initial relative-depth maps. For georeferenced imagery, a lower-resolution DEM source such as SRTM or a limited set of Ground Control Points may be used to map scale-agnostic depth features to absolute metric elevations. For non-georeferenced imagery, relative height may be used directly in the visualization stage.”

“After computing the elevation map, the system should project the original optical image onto a generated 3D terrain mesh and integrate the result with a rendering engine such as Unity, Three.js, or Babylon.js. The interface should support seamless first-person navigation and analysis of structural heights and slopes from arbitrary aerial perspectives.”

1.4 The three key milestones

Elevation Extraction
Use a robust pre-trained monocular depth model to extract geometric and structural representations from single-view optical imagery.
Scale Calibration
Develop a module that converts relative depth to absolute height using scene-level statistics, low-resolution DEMs, semantic priors, or minimal Ground Control Points for georeferenced inputs.
Visualization Layer
Build an immersive, preferably interactive, rendering pipeline that converts the optical texture and derived depth map into a navigable 3D environment deployable as a standalone application.

1.5 Evaluation criteria — this drives every decision in the project

WeightCriterion, as written
50%DSM Estimation — Accuracy and Validation. Evaluate RMSE, MAE, and correlation against LiDAR or reference data, including performance stability across urban, sparse, hilly, and forested landscapes.
50%Visualization — Rendering Quality and User Experience. Assess projection accuracy, visual fidelity, navigability of the 3D flythrough, interface intuitiveness, software stability, and successful standalone deployment.

Half the marks are the front end. This is the single most consequential fact in the problem statement, and it is why roughly half of the engineering effort in this project went into the viewer and the deployment rather than into the model.

1.6 Expected deliverables

“Deliver a fully integrated software suite with complete source code and technical documentation. The solution must be deployable as a unified module containing the following components:”

  • Elevation Estimation Module: accept single-view optical satellite imagery in PNG, JPG, or TIFF format and output a high-fidelity DSM in a standard geospatial format.
  • Interactive Visualization Platform: provide a user-friendly 3D flythrough experience that lets users upload imagery, visualize reconstructed terrain, and validate estimated height values against reference datasets.

Part 2

What the system does, end to end

One optical satellite image goes in. A navigable, measurable 3D surface comes out. This part traces every stage of that path and names the file that performs it.

2.1 The one-sentence description

The claim, stated precisely

DepthWizard takes a single optical satellite photograph and produces a per-pixel map of height above ground in metres, together with a per-pixel statement of how uncertain each of those metres is, then renders that map as a textured 3D surface a user can fly through and take measurements on in a web browser — with no graphics card anywhere in the chain.

2.2 Why one image is hard

Height from imagery is normally obtained one of three ways, and all three need something we are refusing to require:

Conventional methodWhat it needsWhy that is a problem
Stereo photogrammetryTwo photographs of the same ground from different anglesCannot be applied retrospectively. Decades of single-view archive imagery can never gain height.
Airborne LiDARA laser scanner flown over the areaExpensive, slow, requires a flight campaign per area.
InSARRadar satellite pairs with controlled baselinesSpecific sensor availability; computationally heavy.

Single-view height estimation is ill-posed: infinitely many three-dimensional scenes project to the same flat photograph. There is no unique correct answer. That is not a detail — it is the reason this project predicts a distribution per pixel rather than a number, which is covered in Part 5.

2.3 The full pipeline

  RAW ARCHIVE                DFC2019 zip archives (RGB + LiDAR truth + semantic classes)
        |                    tools/prepare_data.py   extract -> probe -> shard
        v
  SHARDED DATA               data/shards/*.npz    518x518 crops, region-disjoint split
        |                    train.py             DA-V2 backbone + twin (mu, log-var) head
        v
  CHECKPOINT                 checkpoints/run02/best.pt   297.1 MB (99.2 MB stripped for serving)
        |                    infer.py             sliding window 518 / overlap 140, cosine blend
        v
  RASTER PRODUCTS            scene.height.tif  scene.sigma.tif   float32 GeoTIFF, metres
        |                    tools/export_terrain.py
        v
  BROWSER BUNDLE             viewer/scenes/<name>/  height.bin sigma.bin truth.bin texture.jpg
        |                                          + manifest.json
        v
  3D FLYTHROUGH              viewer/index.html + main.js + three.js  -> WebGL mesh, measurable

2.4 Stage by stage, with the responsible file

1. Ingest
tools/prepare_data.py unpacks the DFC2019 archives, measures what the documentation does not state (pixel size, void encoding, height range), and writes compressed shards. The probe step exists because the DFC2019 tiles were rewritten by tifffile at some point in their history and lost all georeferencing — nothing in the files says a pixel is 30 cm.
2. Split
Regions are assigned whole to train, validation or test with seed 1337. No tile from a training region can appear in validation. 76 / 16 / 16 regions.
3. Train
train.py fine-tunes Depth Anything V2 Small with a Gaussian negative-log-likelihood objective, two learning rates, and a software thermal governor for the GPU.
4. Score
tools/evaluate.py runs whole 1024×1024 tiles through a sliding window and reports RMSE, MAE, correlation, bias, per-semantic-class error, per-terrain error, per-building error, calibration error, and the σ-versus-error rank correlation.
5. Infer
infer.py runs a scene of any size: tiles it at 518×518 with 140 px overlap, blends with a cosine window, optionally applies 8-fold test-time augmentation, optionally fuses a second pass at 2× zoom, optionally matches the input resolution to the training resolution, optionally anchors to a coarse DEM or to ground control points. Writes GeoTIFFs.
6. Export
tools/export_terrain.py converts the rasters into a browser bundle: raw float32 binaries plus a JSON manifest carrying provenance, geometry, and every statistic the viewer's panels display.
7. Render
viewer/main.js builds a Three.js mesh from the float32 heights, drapes the original photograph over it, and provides four display modes, a drag-to-compare against LiDAR, an error map, a sun-direction control, a tour path, and a two-click measuring tool with calibrated error bars.
8. Serve
tools/serve_app.py exposes the whole thing publicly: the viewer, the baked scenes, and an upload endpoint that runs stages 5–6 on demand.
9. Package
tools/build_standalone.py inlines everything — Three.js, the application code, every scene binary, every texture — into a single 15.16 MB HTML file that runs offline from a double-click.

2.5 The two output products the problem statement asks for

InputProductHow it is produced
PNG / JPG, no spatial metadatarDSM — relative surface modelThe model's height output is used directly. It is metric in the sense that the head was trained to regress metres, but with no location there is no datum to anchor it to, so it is reported as relative.
GeoTIFF with a CRS and transformAbsolute DSM — metric elevationDSM = terrain elevation + above-ground height. The terrain comes from Copernicus GLO-30 fetched for the scene's bounds; the above-ground height is ours. Enabled with --dem auto.
The distinction that most confuses readers

The model predicts AGL — above ground level, also called nDSM or normalised DSM. A 10 m building on a 100 m hill reads 10 m, not 110 m. That is deliberate: it is the quantity that transfers between places, because it does not depend on where sea level is. A DSM is elevation above a vertical datum, so producing one means adding the terrain back. Part 8.6 covers how.

2.6 What makes this more than a depth model with a camera flying through it

  1. Every pixel carries an error bar. The network predicts a Gaussian per pixel, trained with heteroscedastic negative log-likelihood. The claim is falsifiable and was tested: expected calibration error is 0.077 and the rank correlation between predicted uncertainty and actual error is +0.829.
  2. The viewer is a measuring instrument. Two clicks give ground distance, height difference and slope distance in metres, with the uncertainty on the height difference propagated — and calibrated, because the naive combination of two error bars is wrong by a factor of about 3.5 on a single rooftop.
  3. Heights survive the trip to the browser exactly. Terrain ships as raw float32, not as a 16-bit PNG. Browsers decode images through an 8-bit canvas and would silently quantise the metres.
  4. It runs with no GPU. ONNX export, int8 quantisation, CPU inference measured at 509 ms per 518×518 tile, and a live public deployment on a 2-vCPU virtual machine.

3.7 File formats used

GeoTIFF (.tif)
Input imagery and all raster outputs. Carries CRS and affine transform when present. Output height and sigma rasters are float32, single band, metres.
PNG / JPG
Accepted as input for the non-georeferenced path. JPEG is also the scene texture format in the browser bundle.
.npz
Compressed NumPy archives. One shard holds many 518×518 crops with their heights and semantic classes. 92 files: 61 train, 14 val, 14 test, plus three JSON metadata files.
.pt
PyTorch checkpoint. best.pt is 297,134,061 bytes with optimiser, scheduler and RNG state; stripped to 99.2 MB for serving.
.onnx
Exported model. fp32 is 100,672,732 bytes; int8 is 36,814,825 bytes.
.bin
Raw little-endian float32 arrays for the browser: height.bin, sigma.bin, truth.bin, terrain.bin. A 1024×1024 scene layer is exactly 4,194,304 bytes.
.h5
HDF5. The GAMUS dataset stores its height labels as *_AGL.h5.
.IMD
WorldView image metadata. 67 of them carry solar and viewing geometry for the DFC2019 scenes; parsed by tools/parse_imd.py.
JSONL
Append-only training log, one JSON object per line, so a run that dies mid-epoch still plots.
